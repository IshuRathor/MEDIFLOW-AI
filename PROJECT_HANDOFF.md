# MEDIFLOW AI — Project Handoff

This document describes the tracked MEDIFLOW AI project and its local development workflow for teammates. Local `.env` files, databases, virtual environments, dependency folders, logs, and patient records are developer-specific and must not be shared or committed.

## 1. Project at a glance

MEDIFLOW AI (also branded MediFlow in parts of the UI) is a role-based hospital operations web application. It combines a React + TypeScript single-page frontend with a FastAPI REST API, SQLAlchemy persistence, Alembic migrations, SQLite for local development, optional PostgreSQL for shared environments, deterministic symptom triage, and an optional Gemini-powered operational assistant.

The product covers account registration and approval, role-specific dashboards, patient and doctor records, appointments and doctor availability, bills and payments, operational AI chat, and audit events. It is an operations prototype: prescriptions and medical-record modules are explicitly reported as unsupported by the patient dashboard. Triage is a keyword-based urgency suggestion and is not a diagnosis.

Default local development URLs after starting both servers:

- Web app: `http://127.0.0.1:5173/`
- API root: `http://127.0.0.1:8000/`
- Interactive OpenAPI docs: `http://127.0.0.1:8000/docs`
- Health: `http://127.0.0.1:8000/health`
- Readiness: `http://127.0.0.1:8000/health/ready`

## 2. Technology and runtime

### Frontend

- React 19, TypeScript, Vite 8.
- npm scripts in `frontend/package.json`: `dev`, `build`, `lint` (Oxlint), `preview`.
- API URL is `import.meta.env.VITE_API_URL`, falling back to `http://localhost:8000/api` (`frontend/src/api.ts`).
- Vite config only enables the React plugin; it does not proxy API requests.
- Authentication token is persisted in browser `localStorage` under `mediflow_access_token`.

### Backend

- Python FastAPI with Uvicorn; SQLAlchemy 2; Alembic; Pydantic; python-dotenv.
- Pinned dependencies are in `backend/requirements.txt`: FastAPI 0.115.6, Uvicorn 0.34.0, SQLAlchemy 2.0.37, Alembic 1.14.1, python-dotenv 1.0.1, psycopg2-binary 2.9.10, google-genai 1.2.0, python-jose[cryptography] 3.5.0, redis 5.2.1, and email-validator 2.2.0 (required by Pydantic `EmailStr`).
- Local database defaults to `sqlite:///./hospital.db`, relative to the backend working directory. SQLite is configured with `check_same_thread=False`; non-SQLite engines use pre-ping and a connection pool.
- `backend/.env.example` documents all environment variables. Each developer copies it to `backend/.env` and replaces the JWT placeholder with their own randomly generated secret. `.env` is ignored by Git.
- `ENVIRONMENT` defaults to development. Production startup requires a configured JWT key at least 32 characters long and explicit CORS origins.
- Gemini is optional. Without `GEMINI_API_KEY`, AI chat uses deterministic behavior/fallbacks. Redis is optional; rate limiting falls back to in-process memory.

### Start locally (PowerShell)

From repository root, in separate terminals:

```powershell
Set-Location backend
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
# Edit .env and replace JWT_SECRET_KEY with a private value generated by:
python -c "import secrets; print(secrets.token_urlsafe(48))"
python -m alembic upgrade head
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

```powershell
Set-Location frontend
npm ci
npm run dev -- --host 127.0.0.1
```

Backend tests run from `backend/` with `python -m unittest discover -s tests -t .`; the recommended Python environment name is consistently `.venv`. Frontend dependencies are installed reproducibly with `npm ci` using `frontend/package-lock.json`.

Local SQLite is the default and stores `hospital.db` relative to the backend working directory. For a deliberately shared PostgreSQL environment, each developer configures a private `DATABASE_URL` in their own `.env`; never share a local SQLite file. `VITE_API_URL` is optional and defaults to `http://localhost:8000/api`. `GEMINI_API_KEY` and `REDIS_URL` are optional for local core workflows.

Use Python 3.12.x, Node.js 20.19+ (20.x) or 22.12+, and npm 10+. Those Node minimums match Vite 8's engine requirement. Create the backend environment as `.venv` from `backend/`; Alembic and the application default to local SQLite. Run `python -m alembic upgrade head` there to apply migrations. The README covers installation, configuration, production, backup/restore, and validation.

## 4. User experience and frontend behavior

`frontend/src/App.tsx` is a single large React module containing the authentication screen, resource lists, create/edit forms, scheduling widgets, dashboard renderers, AI chat, and triage modal. `frontend/src/api.ts` defines wire types and fetch helpers.

### Login and registration

- Login asks the user to choose a role and sends email, password, and role to `/api/auth/login`. The current backend authenticates the email/password and returns the actual user role; it does not compare that role with the submitted role field.
- Registration asks for name, phone, email, password and confirmation, and lets the user select patient, clinician, staff, or admin. Clinician registration additionally requests specialization, department, and years of experience.
- The first user in an empty users table is created as an active, approved administrator regardless of selected role. After that, patient registrations are immediately active/approved, while clinician/staff/admin public registrations are inactive and pending administrator approval.
- The app stores a JWT in local storage, fetches `/auth/me`, then loads the role dashboard and records. Invalid/expired token clears local storage and returns to login.
- There is an administrator account modal, pending approval list with approve/reject buttons, and sign-out control.

### Role navigation

- Patient: Overview only in the left nav; overview includes upcoming/previous appointments, bills, assigned doctor, and an appointment-booking widget. Its dashboard buttons can switch to Appointments/Billing content even though those labels are not in patient left navigation.
- Clinician: Overview, Appointments, Patients, Doctors. Overview contains appointment stats, schedule, assigned patients, and recurring/specific-date availability editor.
- Finance staff (`staff`): Overview, Appointments, Patients, Doctors, Billing. Overview contains revenue, collections, outstanding bills, transactions, and billing shortcuts.
- Administrator: Overview, Appointments, Patients, Doctors, Billing, Accounts. Overview includes hospital counts, revenue, pending bills/approvals, department statistics, recent appointments, and audit activity.
- All authenticated roles have top-bar controls for MediFlow AI chat and symptom triage. The top-bar search and notification icons are visual controls without a developed search/notification flow in this frontend.

### Resource actions

- Patient modal: name, email, age, optional gender and phone.
- Doctor modal: name, email, specialization, department, phone and experience.
- Appointment modal: patient, doctor, datetime, optional reason.
- Bill modal: patient, bill number and amount.
- Payment modal: bill, amount, method.
- Admin account modal: role and account details; patients are associated with an existing patient record.
- Resource page supports adding/listing and selected deletion/cancellation. UI asks for browser confirmation before deletions/cancellations.
- Patient booking widget fetches available slots by selected doctor/date and books a selected slot.

### AI and triage UI

- Triage modal collects symptoms (max 500 characters), returns urgency, recommended department/action, safety notice and disclaimer.
- Chat collects an operational query (3–2,000 chars), retains the conversation ID in React state, displays message/status/tool trace, and presents approve/reject actions for proposals.
- A refresh of the browser resets the chat conversation ID state, though server-side history remains stored by user and conversation ID.

## 5. Backend routes

All routers below are mounted under `/api`. Except auth and health/root routes, the app mounts operational routers with `get_current_user`, so a bearer JWT is required. Individual handlers enforce additional role and ownership checks. See `/docs` for exact schemas, query parameters and response shapes.

### Authentication — `/api/auth`

| Method and path | Purpose |
|---|---|
| `GET /registration-status` | Reports whether user table is empty and first registration is available. |
| `POST /register` | First admin or later public patient/clinician/staff/admin registration. |
| `POST /register-patient` | Compatibility patient-only registration endpoint. |
| `POST /login` | Verify password/status and issue bearer JWT. |
| `GET /me` | Return current authenticated user. |
| `POST /refresh` | Issue a new access token for authenticated user. |
| `POST /users` | Admin creates a staff/clinician/patient account; patient accounts link to an existing patient record. |
| `GET /users` | Admin lists accounts. |
| `GET /pending-users` | Admin lists pending registrations. |
| `POST /users/{user_id}/approve` | Admin activates and approves pending account; writes explicit audit event. |
| `POST /users/{user_id}/reject` | Admin rejects pending account; writes explicit audit event. |

Passwords use PBKDF2-HMAC-SHA256 (600,000 iterations, per-password random salt); tokens are HS256 JWTs with subject=email, role, access-token type, JTI and expiry (default 60 minutes). Active and approved account state is rechecked on every authenticated request. Role is stored in JWT but authorization also uses the database user.

### Patients — `/api/patients`

`POST /` creates (admin/staff/clinician); `GET /` lists with search, pagination and sort controls; `GET /{patient_id}` gets one; `PUT /{patient_id}` updates (admin/staff/clinician); `DELETE /{patient_id}` deletes (admin/staff). Patient users are restricted to their linked patient record for list and detail queries; the list applies ownership before optional search, sorting, and pagination.

### Doctors — `/api/doctors`

`POST /` creates (admin/staff); `GET /` lists with search/specialization, pagination and sort; `GET /{doctor_id}` gets one; `PUT /{doctor_id}` updates (admin/staff); `DELETE /{doctor_id}` deletes (admin only). Doctor records can be linked one-to-one to clinician users.

### Appointments — `/api/appointments`

`POST /` creates an appointment; `GET /` lists with filters/pagination; `GET /{appointment_id}` gets one; `PUT /{appointment_id}` updates; `DELETE /{appointment_id}` cancels (soft status update). Handlers scope patient users to their owned record and clinicians to their linked doctor for appointment operations. Appointments have Scheduled, Completed, Cancelled, and No-show statuses. Database partial unique indexes prevent a Scheduled duplicate for the same doctor/time or same patient/time.

### Availability — `/api/availability`

| Method and path | Purpose |
|---|---|
| `POST /` | Add recurring weekday hours or a date-specific rule/block. Clinician edits their linked doctor; admin/staff pass `doctor_id`. |
| `GET /me` | Get own availability (clinician). |
| `GET /slots/{doctor_id}?date=YYYY-MM-DD` | Generate slots using doctor duration and existing Scheduled appointments; may return alternate dates. |
| `GET /doctor/{doctor_id}` | List a doctor's rules. |
| `PUT /{availability_id}` | Update a rule; clinician is limited to own doctor, admin/staff allowed. |
| `DELETE /{availability_id}` | Delete a rule with the same role boundary. |

Availability exceptions for a specific date supersede recurring weekday rules. A date-specific unavailable rule blocks that date. Slot generation uses `appointment_duration_minutes` (default 30, minimum effective duration 5 minutes), detects overlap, rejects past dates, and reports up to seven alternate available dates searched within the next 14 days.

### Billing and payments

`/api/bills`: `POST /` creates (admin/staff); `GET /` lists with search/status/pagination (patient scoped); `GET /{bill_id}` retrieves (patient ownership checked); `PUT /{bill_id}` updates (admin/staff); `DELETE /{bill_id}` deletes (admin). Bill statuses: Pending, Partially Paid, Paid, Cancelled.

`/api/payments`: `POST /` records payment (admin/staff); `GET /` lists (patient scoped); `GET /{payment_id}` retrieves (patient ownership checked); `DELETE /{payment_id}` deletes (admin). Payment methods include Cash, Card, Bank Transfer, Insurance, Other. Completed payments update bill status automatically and overpayment/cancelled-bill payments are rejected. Payments have Pending, Completed, Failed, Refunded statuses.

Money uses SQL Numeric/Decimal on models, although some route query inputs use floats and responses convert amounts to floats in parts of the API.

### Dashboards — `/api/dashboard`

- `GET /metrics`: shared summary counts/amounts, scoped for patient and clinician where applicable.
- `GET /doctor`: clinician-only schedule, stats, assigned patients, recent visits, availability.
- `GET /patient`: patient-only personal schedule, bills, payments, current/latest doctor. Prescriptions and medical records return `{supported:false, items:[]}`.
- `GET /finance`: staff-only revenue/collection/outstanding-bill metrics and recent transactions.
- `GET /admin`: administrator-only hospital stats, departments, recent appointments/activity and pending approvals.

### Triage — `/api/triage`

`POST /` accepts `{ "symptoms": "..." }` and returns urgency (`Low`, `Medium`, `High`, `Emergency`), recommended department, original symptom summary, action, disclaimer and safety notice. It is deterministic substring matching in `services/triage_service.py`, not a generative model or diagnosis. Emergency phrase matches explicitly advise local emergency services/immediate care; unknown symptoms default to Low / General Medicine with a general evaluation suggestion.

### Operational AI — `/api/ai`

| Method and path | Purpose |
|---|---|
| `POST /chat` | Query `{query, conversation_id?}`; returns conversation ID, agent, status, message, structured data, trace and optional approval ID. |
| `POST /approvals/{approval_id}/{approve\|reject}` | Decide an explicitly proposed sensitive operation. Approval belongs to its requesting user and expires after ten minutes. |
| `DELETE /conversations/{conversation_id}` | Delete current user's messages and approvals for conversation. |

Chat has a per-user limit of 20 requests/minute. Conversation messages and approvals are user-scoped. Write operations are represented as expiring pending approvals; database operations are executed only after approval and are checked for owner/role/status. The endpoint guards against cross-user conversation/approval access and uses a conditional status update to avoid duplicate concurrent execution.

Current registered tools include: `support_guidance`, `get_patient`, `search_patients`, `search_doctors`, `doctor_availability`, `find_available_slots`, `appointment_history`, `financial_summary`, `monthly_financial_comparison`, `pending_bills`, `expense_summary`, `payment_history`, plus approval-write proposals for `create_appointment`, `cancel_appointment`, `reschedule_appointment`, `generate_bill`, and `record_payment`. Registry role lists and scoped query behavior are in `ai/orchestrator.py`; tool schemas and role checking live in `ai/tool_registry.py`. Gemini 2.5 Flash function declarations are used when configured; deterministic routing provides fallback and triage is evaluated before general model routing.

### Root and health

- `GET /` identifies the API.
- `GET /health` is a basic process response.
- `GET /health/live` is liveness.
- `GET /health/ready` executes `SELECT 1` and reports DB state plus whether Gemini is configured. It does not validate every downstream service.

## 6. Data model

All models use SQLAlchemy and are under `backend/app/models/`.

| Table/model | Main data and relationships |
|---|---|
| `users` / `User` | Unique email, full name, password hash, role, active flag, approval status, created timestamp. One-to-one optional Patient and Doctor links. |
| `patients` / `Patient` | Name, nullable age/gender/phone/email, unique optional `user_id` FK to users (SET NULL), created timestamp. Age DB check 0–130. |
| `doctors` / `Doctor` | Name, specialization, phone/email, department, experience, unique optional user link, appointment duration default 30 minutes, created timestamp. |
| `appointments` / `Appointment` | Patient and doctor FKs, datetime, reason, status, notes, created time. Partial unique scheduled indexes per doctor/time and patient/time for SQLite/Postgres. |
| `doctor_availability` / `DoctorAvailability` | Doctor FK, weekday, start/end times, available flag, optional specific date. |
| `bills` / `Bill` | Patient FK, unique bill number, Numeric(12,2) amount, status, created time. Cascades to items and payments. Nonnegative total check. |
| `bill_items` / `BillItem` | Bill FK, description, quantity, unit price, amount; checks positive quantity and nonnegative amounts/prices. |
| `payments` / `Payment` | Bill FK, amount, method/status, optional unique transaction reference, paid timestamp. Positive amount check. |
| `expenses` / `Expense` | Description, category, amount, method, expense date and created time; nonnegative amount. Used in finance summary tooling. |
| `ai_conversation_messages` | Conversation ID, user FK, role/content, optional trace JSON, timestamp. |
| `ai_approvals` | Approval ID, conversation/user, action and JSON parameters, pending/approved/rejected/expired/executed state, expiration/execution and result. DB status check. |
| `audit_logs` | Optional actor FK, action/resource/resource ID, method/path/status, optional JSON metadata, timestamp. |

Migration history contains an initial schema and follow-up migrations for patient ownership, AI conversation/approval records, audit logs, approval-state constraint, registration approval fields and scheduling exceptions/duration. Alembic versions are under `backend/migrations/versions/`.

## 7. Authorization and security design

- JWT bearer auth is applied at router inclusion for operational APIs; auth registration/login and root/health are public.
- `require_roles(...)` centralizes several create/update/delete role checks. Many reads and record ownership checks live directly in route handlers.
- Patient accounts link to one Patient row; patient query endpoints for appointments, bills, payments and dashboards filter to this linked record. Clinician accounts link to one Doctor row; scheduling and clinician dashboard operations use that link.
- `get_current_user` loads the user from DB after JWT verification and rejects inactive/pending/rejected accounts.
- Passwords are not stored plaintext. Access tokens are stored in localStorage by the current frontend, which has XSS tradeoffs and should be considered for production hardening.
- Middleware adds request IDs, JSON request logs, security headers, `Cache-Control: no-store` on `/api/*`, and audit rows for every POST/PUT/PATCH/DELETE response. Specific account approval actions also write detailed audit rows.
- Production mode validates JWT secret strength and CORS allowlist. HSTS is added in production.
- Rate limiting supports Redis with process-local fallback. The fallback is not shared between server workers/instances.
- There is no evidence in this repo of an external payment processor, prescription system, clinical records system, email/SMS delivery, or deployment infrastructure. Treat those as unimplemented until confirmed elsewhere.

## 8. AI design and boundaries

The current chat path is `api/ai.py` → `run_orchestrator` → registered tool definitions and permission/argument checks. It can return structured operational data and trace items, request clarification, or ask for approval. Tools use SQLAlchemy DB state rather than arbitrary SQL or arbitrary code. Gemini is configured via environment key; otherwise fallback logic is used. Chat stores user-scoped conversation messages and traces in DB.

Sensitive actions (appointment create/cancel/reschedule; bill generation/payment proposal) need explicit approval, with a 10-minute expiry. For agent changes, preserve: role-specific tool access, patient/doctor ownership scoping, schema validation, no arbitrary execution, approval expiration, idempotent one-time execution, and deterministic behavior during model outage. Keep medical advice bounded; the triage service itself is basic keyword matching and includes safety language.

## 10. Known review points / limitations for the next AI

1. **Patient isolation:** Patient ownership is applied before optional search, sorting and pagination on `GET /api/patients/`. Regression assertions cover matching the caller's record and exclude another patient's name/email search results.
2. **One-file frontend:** Most screens and API state orchestration live in `App.tsx`; separate components/hooks if making substantial UI changes, while preserving the current API contracts.
3. **UI/API role alignment:** Review endpoints and nav actions together. Backend authorization remains authoritative.
4. **Legacy AI files:** Verify whether a requested AI change belongs in the registered orchestrator or a legacy agent. The live `/api/ai/chat` imports the orchestrator.
5. **SQLite and local state:** Each developer should use a private local database unless a shared PostgreSQL database is deliberately provisioned. Never disclose patient data or commit local DB files.
6. **Operational incompleteness:** CI is defined in `.github/workflows/ci.yml`; there is no Docker setup or live external payment integration. Prescription/medical-record modules are unsupported, and deployment/clinical validation require separate work.
7. **Frontend presentation:** `frontend/index.html` still has the generic title `frontend`; top-bar search and notifications are not wired to backend behavior.
8. **Medical scope:** Triage is a deterministic heuristic and not a diagnosis. Do not present it as validated clinical decision support.

## 11. Guidance for the next AI

Before editing, inspect `README.md`, relevant `backend/app/api` routes and schemas, linked models, and relevant frontend fetch functions. Keep database migrations in sync with model changes. Preserve existing role/ownership protections and approval checks. Add tests only when the user asks for tests or verification; otherwise do not imply test execution. Never read or reproduce secrets from `.env` or actual patient/billing records from the local database unless explicitly needed for an authorized task.

For team workflow, see `CONTRIBUTING.md`. Do not reset or clean a developer's worktree as part of routine setup; inspect and preserve local changes before switching branches or pulling.
